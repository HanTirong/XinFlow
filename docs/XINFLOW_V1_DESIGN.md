# 薪流（XinFlow）V1 产品与工程设计手册

> 文档状态：V1 开发基线  
> 更新时间：2026-09-21
> 适用范围：Android、iOS 本地版  
> 代码仓库：`HanTirong/XinFlow`

## 1. 文档目的

本文档是薪流 V1 的产品、交互、数据和工程实现基线，用于指导需求拆分、编码、测试、数据迁移和版本验收。

当实现细节与本文档冲突时，应先更新本文档并记录原因，再修改代码。影响金额计算、工资周期、备份兼容性的变更必须同时补充测试和迁移方案。

## 2. 产品定义

薪流不是一款追求完整财务管理能力的传统记账应用。它只解决一个核心问题：

> 以实际工资到账为周期，记录每一笔工资最终去了哪里，并让用户随时知道本期工资还剩多少。

核心恒等式：

```text
本期工资 + 正余额结转 = 净消费 + 净存款 + 净理财 + 当前剩余
```

其中：

- 存款和理财属于工资去向，会减少当前剩余，但不计入消费。
- 退款冲减原消费，并增加当前剩余。
- 提取冲减原存款或理财，并增加当前剩余。
- 允许当前剩余为负数，负数表示本期支出或分配已经超过工资。
- 统计周期由用户实际确认工资到账的时间决定，不等同于自然月。

英文品牌名为 **XinFlow**，中文显示名为 **薪流**。推荐应用标识使用 `com.hantirong.xinflow`，在首次商店发布前完成唯一性确认，此后不再修改。

## 3. 产品原则

1. **工资周期优先**：所有流水必须归属一个明确的工资周期。
2. **录入极简**：常规记录只要求金额和分类，其余信息均为可选。
3. **分析后置**：不把复杂选择放在输入端，统计逻辑在报告端完成。
4. **本地优先**：V1 不依赖服务器、账号或网络即可完整使用。
5. **金额可靠**：金额使用整数分存储，禁止使用浮点数参与财务计算。
6. **历史可追溯**：封存周期、退款、删除和导入冲突都必须留下可解释的数据状态。
7. **升级不丢数据**：应用升级通过数据库迁移保留数据，不要求用户重新导入。

## 4. 已确认的 V1 决策

以下四项已经确认，是 V1 的固定规则：

### 4.1 上期正余额仅允许手动结转

关闭旧周期时保存其最终剩余。新周期默认只使用新工资金额；用户可在周期切换时明确勾选，将大于零的上期剩余写入新周期独立的 `carryover_cents` 字段。负余额不能结转。

结转不得改写新工资金额，也不得静默发生。

### 4.2 退款使用独立退款记录

普通录入金额始终为正数。退款通过“退款记录”冲减一笔原消费，不允许用户以普通负数流水代替退款。

退款记录必须关联原消费，累计退款金额不能超过原消费的有效金额。

### 4.3 存款与理财提取使用独立冲减记录

提取记录必须关联原存款或理财分配，允许多次部分提取，但累计有效提取不得超过原分配金额。普通流水仍不接受负数金额。

### 4.4 历史周期默认只读

周期封存后，普通入口只能查看。确需修改时，用户必须进入独立的“修正历史周期”流程，并看到修改会改变历史报告的明确提示。

修正完成后重新计算该周期报告并更新修改时间，但不能改变周期 ID、实际开始时间或实际结束时间。

## 6. 术语

| 术语 | 定义 |
|---|---|
| 工资周期 | 从一次用户确认工资到账，到下一次确认工资到账之前的时间段 |
| 当前周期 | 唯一处于 `active` 状态的工资周期 |
| 封存周期 | 已结束且处于 `closed` 状态的工资周期 |
| 分配 | 消费、存款和理财对本期工资的占用 |
| 净消费 | 消费金额减去有效退款金额 |
| 当前剩余 | 工资加正余额结转，再减去净消费、净存款和净理财 |
| 预计发薪日 | 根据用户设置计算出的提示日期，只用于倒计时 |
| 实际工资到账 | 用户主动确认后发生的周期切换事件 |

### 7.2 架构边界

```text
View
  ↓ 用户事件 / UI 状态
ViewModel / Controller
  ↓ 用例调用
Domain Service
  ↓ 数据接口
Repository
  ↓
Drift Database / File Service / Platform Plugin
```

- View 只负责显示、布局、动画和触发命令。
- ViewModel 负责页面状态、输入校验和展示模型转换。
- Domain Service 负责工资周期切换、退款和备份合并等跨表业务事务。
- Repository 是业务数据的唯一读写入口。
- UI 不得直接调用 Drift DAO 或文件插件。
- Repository 之间不直接互相依赖；跨聚合事务由 Domain Service 协调。

## 8. 数据模型

所有可备份实体都包含：

```text
id          TEXT UUID PRIMARY KEY
created_at  INTEGER UTC milliseconds
updated_at  INTEGER UTC milliseconds
deleted_at  INTEGER UTC milliseconds NULL
```

`deleted_at` 用于合并恢复时保留删除事实。V1 不执行自动物理清理。

### 8.1 salary_cycles

| 字段 | 类型 | 规则 |
|---|---|---|
| id | TEXT | UUID 主键 |
| salary_cents | INTEGER | 大于或等于 0 |
| carryover_cents | INTEGER | 大于或等于 0；仅由显式正余额结转产生 |
| started_at | INTEGER | 用户确认工资到账的实际时间 |
| expected_pay_date | TEXT | `YYYY-MM-DD`，创建周期时保存的预计日期快照 |
| closed_at | INTEGER NULL | 封存时间 |
| status | TEXT | `active` 或 `closed` |
| final_remaining_cents | INTEGER NULL | 封存时的最终剩余 |
| created_at | INTEGER | UTC 毫秒 |
| updated_at | INTEGER | UTC 毫秒 |
| deleted_at | INTEGER NULL | 预留软删除能力；本地数据页可在确认后物理删除历史周期 |

数据库必须保证未删除记录中最多存在一个 `active` 周期。应用启动时如发现多个活动周期，应停止金额写入并进入数据修复状态，不能自行猜测保留哪一个。

### 8.2 transactions

| 字段 | 类型 | 规则 |
|---|---|---|
| id | TEXT | UUID 主键 |
| salary_cycle_id | TEXT | 外键，必填 |
| entry_kind | TEXT | `allocation`、`refund` 或 `withdrawal` |
| flow_type | TEXT | `expense`、`saving` 或 `investment` |
| amount_cents | INTEGER | 严格大于 0 |
| category_id | TEXT | 一级分类 ID |
| subcategory_id | TEXT NULL | 二级分类 ID |
| reverses_transaction_id | TEXT NULL | 退款或提取时必填，指向原分配 |
| occurred_at | INTEGER | 实际或补记时间，UTC 毫秒 |
| occurred_on | TEXT | 用户认知中的本地日期，`YYYY-MM-DD` |
| note | TEXT NULL | 可选，限制合理长度 |
| created_at | INTEGER | UTC 毫秒 |
| updated_at | INTEGER | UTC 毫秒 |
| deleted_at | INTEGER NULL | 软删除时间 |

设计要求：

- `flow_type` 是流水创建时的性质快照，防止分类调整改变历史汇总。
- `allocation` 的 `reverses_transaction_id` 必须为空。
- `refund` 只能关联未删除的 `expense/allocation`。
- 一笔消费可对应多笔退款，但有效退款总额不能超过原消费金额。
- 一笔存款或理财可对应多笔提取，但有效提取总额不能超过原分配金额。
- 退款默认继承原消费的周期和分类，不允许跨周期创建。
- 删除原消费前，必须同时处理其退款；推荐将整组记录一并软删除。

### 8.3 categories

一级、二级分类使用一张自关联表，避免两套几乎相同的读写逻辑。

| 字段 | 类型 | 规则 |
|---|---|---|
| id | TEXT | UUID 主键；默认分类使用固定稳定 ID |
| parent_id | TEXT NULL | 一级分类为空，二级分类指向一级分类 |
| name | TEXT | 同级未删除分类名称不可重复 |
| flow_type | TEXT | `expense`、`saving` 或 `investment` |
| icon_key | TEXT | 应用内图标键，不保存平台资源路径 |
| color_key | TEXT | 统一主题色键 |
| sort_order | INTEGER | 同级显示顺序 |
| show_on_home | INTEGER | 仅一级分类可作为首页快捷项 |
| sort_order | INTEGER | 显示顺序 |
| is_system | INTEGER | 默认分类标记 |
| is_active | INTEGER | 停用后不出现在新建入口，历史仍可显示 |
| created_at | INTEGER | UTC 毫秒 |
| updated_at | INTEGER | UTC 毫秒 |
| deleted_at | INTEGER NULL | 软删除时间 |

规则：

- 二级分类必须继承一级分类的 `flow_type`。
- 已被流水引用的分类只能改名或停用，不能物理删除。
- 已产生流水后，不允许直接改变分类性质；需要新建另一性质的分类。
- 默认分类 ID 必须跨安装保持一致，保证备份合并稳定。

### 8.4 app_settings

V1 使用单行强类型设置表，不使用任意字符串键值存储核心配置。

| 字段 | 类型 | 规则 |
|---|---|---|
| singleton_id | INTEGER | 固定为 1 |
| salary_day | INTEGER | 1 至 31 |
| currency_code | TEXT | V1 固定 `CNY` |
| onboarding_completed | INTEGER | 布尔值 |
| theme_mode | TEXT | `system`、`light`、`dark` |
| updated_at | INTEGER | UTC 毫秒 |

### 8.5 可选操作日志

建议增加 `audit_events`，用于记录高价值本地操作：

- 周期创建与封存
- 历史周期修正
- 备份导出
- 恢复结果
- 数据库迁移结果

日志不得记录完整备注、文件路径或不必要的财务明细。它不上传服务器，只用于本地故障诊断。

## 9. 金额与统计规则

### 9.1 金额表示

- 输入层接受最多两位小数的十进制字符串。
- 解析完成后立即转换为整数分。
- 数据库、领域模型和计算过程统一使用 64 位整数。
- 格式化仅发生在 UI 边界。
- 禁止通过 `double * 100` 直接转换金额。

示例：

```text
用户输入 "123.45" → 解析为 12345 分 → 数据库存储 12345
```

### 9.2 汇总公式

对一个工资周期，忽略软删除记录：

```text
消费分配 = expense/allocation 合计
消费退款 = expense/refund 合计
净消费 = 消费分配 - 消费退款
净存款 = saving/allocation 合计 - saving/withdrawal 合计
净理财 = investment/allocation 合计 - investment/withdrawal 合计

已分配 = 净消费 + 净存款 + 净理财
当前剩余 = salary_cents - 已分配
```

所有首页和报告汇总必须从同一套 Repository 查询或领域计算函数产生，禁止页面分别复制公式。

### 9.3 日期和时区

- 精确时间使用 UTC 毫秒保存。
- 用户选择的记账日期另存为 `occurred_on`，避免用户跨时区后日期发生偏移。
- 日期分组和日报以 `occurred_on` 为准。
- 周期归属以 `salary_cycle_id` 为准，不能根据日期动态推断。
- 工资周期起始日必须由用户设置的固定发薪日推导，不能使用首次打开 App 或点击确认的时间代替。
- 当前周期起始日取今天或今天之前最近一次固定发薪日，结束日取下一个月对应的固定发薪日。
- 月份没有设置的发薪日时，预计发薪日取当月最后一天，例如 31 日设置在 2 月取 2 月最后一天。

## 10. 工资周期状态机

```text
无周期
  └─ 创建首个周期 ──> active

active
  ├─ 新增/修改/删除流水 ──> active
  └─ 确认工资到账
       ├─ 封存旧周期 ──> closed
       └─ 创建新周期 ──> active

closed
  ├─ 普通查看 ──> closed
  └─ 明确进入历史修正 ──> 重新计算后仍为 closed
```

“封存旧周期”和“创建新周期”必须处在同一个数据库事务中：

1. 验证当前活动周期存在。
2. 计算旧周期最终剩余。
3. 将旧周期更新为 `closed`，写入 `closed_at` 和最终剩余。
4. 使用新工资创建新周期；周期起始日取固定发薪日，确认时间只记录实际操作时间。
5. 验证仍然只有一个活动周期。
6. 提交事务。

任一步失败则全部回滚。预计发薪日到达时只显示提醒，不执行上述事务。

## 12. 页面结构

底部导航固定为：

```text
首页｜流水｜月报｜我的
```

### 12.1 首次启动

```text
品牌欢迎页
  → 设置固定发薪日
  → 输入当前工资金额
  → 确认创建首个工资周期
  → 首页
```

在首个周期创建成功前，`onboarding_completed` 不得写为真。中途退出后应回到未完成步骤，而不是进入空首页。

### 12.2 首页

视觉优先级从高到低：

1. 本期工资剩余
2. 本期已分配
3. 消费、存款、理财简要拆分
4. 距离预计发薪日
5. “记一笔”主按钮
6. 常用分类
7. 最近 3 至 5 条流水
8. “工资到账”入口

首页不放复杂图表。余额为负时使用克制的警示色和“本期已超出工资”说明，不阻止继续记账。

- 标题下只显示弱化的周期日期和历史周期入口，不增加“当前工资周期”前缀。
- 剩余金额下使用无文字的细横向进度条，不使用圆环进度。
- 常用分类以 2×4 小卡片展示，“编辑分类”进入分类管理；“记一笔”为分类宫格下方的独立整宽主按钮。
- 最近记录默认展示 3 条，点击当前周期的普通分配记录可进入编辑。
- 浅色和深色主题均使用低饱和色、统一圆角，减少渐变、描边、阴影和发光。
- 一级分类的 `id、name、icon、iconColor、backgroundColor、type` 必须由统一分类视觉配置解析；首页、流水和月报禁止各自维护图标或颜色映射。

### 12.3 记一笔

推荐主流程：

```text
输入金额
  → 选择一级分类
  → 选择二级分类
  → 保存
```

“日期”和“备注”放入可展开的更多选项。默认日期为今天，默认周期为当前活动周期。

保存后：

- 立即返回首页或流水页。
- 显示短暂成功反馈。
- 首页余额和最近记录必须由数据库流更新，不能只在内存中临时加减。
- 防止按钮重复点击产生双记录。

### 12.4 流水

- 默认显示当前周期。
- 支持通过底部弹窗中的纵向滚轮切换历史周期；滚轮居中高亮、自动吸附并默认定位当前周期。
- 周期选项只来自数据库中已经创建的真实周期，不生成未来周期，统一显示为 `YYYY-MM-DD ～ YYYY-MM-DD`。
- 按 `occurred_on` 分组，组内按 `occurred_at` 倒序。
- 支持按消费、存款、理财筛选。
- 当前周期允许修改和软删除。
- 历史周期默认隐藏修改操作，入口放在“修正历史周期”流程中。
- 退款在列表中明确显示为原消费的冲减，不能伪装成收入。

### 12.5 工资到账

确认页显示：

- 旧周期工资、消费、存款、理财和最终剩余
- 新工资金额输入框
- 新周期预计发薪日期
- “上期剩余不会自动计入新周期”的明确说明

用户最终确认后调用原子周期切换事务。

### 12.6 月报

第一层回答“工资去了哪里”：

- 工资总额
- 净消费
- 净存款
- 净理财
- 最终剩余

第二层展示：

- 消费分类占比
- 每日净消费趋势
- 与上一周期的金额和比例变化

比较上一周期时必须展示两个周期的实际起止日期，避免用户误以为是自然月比较。

### 12.7 我的

- 安卓每日记账通知：默认关闭、默认 21:00、可调整时间；通知不包含金额或备注，点击后先经过应用锁再进入记账；使用非精确提醒，不读取微信数据

## 14. 备份与恢复

### 14.1 文件格式

推荐文件名：

```text
xinflow-backup-YYYYMMDD-HHmmss.xinflow
```

`.xinflow` 是 ZIP 容器。未加密 v2 与兼容的 v1 包含：

```text
manifest.json
data.json
checksum.sha256
```

`manifest.json` 示例：

```json
{
  "format": "xinflow-backup",
  "backupVersion": 2,
  "appVersion": "0.1.0",
  "databaseSchemaVersion": 3,
  "exportedAt": "2026-09-19T12:00:00Z",
  "currencyCode": "CNY",
  "dataFile": "data.json",
  "dataSha256": "...",
  "encrypted": false
}
```

`data.json` 包含设置、分类、工资周期、流水、预算以及这些实体的软删除记录。导出顺序固定，便于测试和排查，但恢复逻辑不能依赖数组顺序。

加密备份只包含 `manifest.json` 与 `data.enc`。数据使用 PBKDF2-HMAC-SHA256（随机盐、210000 次迭代）派生 256 位密钥，并使用 AES-256-GCM 提供保密性和完整性。密码至少 8 个字符，应用不保存密码；密码错误或密文损坏必须在任何数据库写入前失败。当前版本继续读取未加密 v1 备份。

### 14.2 导入预检

任何数据库写入之前完成：

1. 验证扩展名和 ZIP 结构。
2. 限制压缩包、解压后文件和实体数量上限，防止异常文件耗尽存储。
3. 验证 `format` 和 `backupVersion`。
4. 未加密备份校验 `data.json` 的 SHA-256；加密备份先完成 GCM 认证解密再校验明文摘要。
5. 完整解析 JSON 并验证必填字段、枚举、金额和外键。
6. 生成导入预览：新增、更新、跳过、删除标记、冲突和不兼容数量。
7. 用户确认预览后才开始合并。

### 14.3 合并规则

合并以实体 ID 为主键：

- 本地不存在：插入导入实体。
- 本地存在且标准化内容相同：跳过。
- ID 相同但内容不同：`updated_at` 较新的实体胜出。
- 较新的 `deleted_at` 胜过较旧的有效记录，防止旧备份复活已删除数据。
- 时间完全相同但内容不同：标记冲突，不自动覆盖；V1 默认保留本地并在结果中报告。
- 默认分类按固定 ID 合并，不按名称猜测。
- 任何工资周期或流水违反不变量时，整次导入失败。

整个合并必须在一个数据库事务中执行。失败时回滚全部变更。

### 14.4 幂等性要求

同一备份连续导入两次，第二次必须：

- 新增 0 条；
- 更新 0 条；
- 不产生重复流水；
- 不改变任何汇总结果。

## 15. 数据库迁移与兼容性

- Drift 的 `schemaVersion` 管理本机数据库结构。
- `backupVersion` 管理导出文件结构。
- 两个版本号独立演进。
- 每次数据库结构变化都必须提供从上一正式版本升级的迁移。
- 迁移前后必须验证周期数量、流水数量、总金额和活动周期唯一性。
- 不允许通过删除并重建数据库解决正式版升级问题。
- 新版本可以读取旧备份时，应先在内存模型中升级备份数据，再写入当前数据库。
- 无法安全读取的新版本备份必须拒绝导入，并给出明确错误，不能部分导入。

## 16. 错误处理

错误按用户可恢复性分类：

| 类型 | 示例 | 处理方式 |
|---|---|---|
| 输入错误 | 金额为空、退款超额 | 就地提示，不调用 Repository |
| 可重试错误 | 文件选择取消、临时文件失败 | 保留页面状态，允许重试 |
| 数据冲突 | 导入同 ID 同时间不同内容 | 保留本地并显示冲突报告 |
| 数据不一致 | 多个活动周期、断裂外键 | 禁止继续写入，进入修复提示 |
| 不兼容 | 备份版本过新 | 拒绝导入，不修改数据库 |

面向用户的错误不能只显示异常类名。调试日志可以记录错误码和堆栈，但不得记录完整备份内容或用户备注。

## 17. 隐私与安全

- V1 不申请网络权限来实现产品功能。
- 数据保存在应用沙盒中的 SQLite 数据库。
- 不接入广告、分析 SDK 或第三方用户画像 SDK。
- 日志不记录完整金额流水、备注或备份正文。
- Android 发布配置不得把签名文件或密码提交到仓库。
- iOS 签名证书和配置文件不进入仓库。
- 备份导出后由用户选择保存位置，应用应明确提示其敏感性。
- 金额隐藏开启后首页默认不展示具体金额，并允许用户临时查看。
- 应用进入后台时使用本地遮挡页，避免系统最近任务缩略图泄露财务数据。
- 应用锁调用系统身份验证并允许系统设备密码回退；应用不读取或保存生物特征。
- 加密备份必须使用经过审查的标准算法和带认证加密，不能自行设计算法。

## 18. UI 与视觉规范

### 18.1 方向

- 蓝色或蓝灰色体系
- 简洁、克制、现代、轻工具感
- 不模仿银行 App，也不模仿复杂传统记账 App
- 首页不堆叠图表
- 金额清晰，但避免到处使用货币符号装饰

### 18.2 Logo 原则

- “薪”是主体，“流”通过笔画走势表达。
- 第一眼必须能辨认“薪”。
- 水感只体现在笔画气质，不增加独立水滴、波浪或浪花。
- 以已选定的“05：品牌化版·中水感版”为视觉基准。
- 高清化只还原原字形和比例，不重新设计草字头、整体骨架或水流笔画。

正式接入 App Icon 前，源文件、透明背景版本、Android adaptive icon 前景/背景和 iOS 方形母版应统一归档。

### 18.3 可访问性

- 正文和关键金额满足可读对比度。
- 不能只依赖红、绿颜色表达状态。
- 支持系统字体缩放，关键金额不截断。
- 所有可点击控件提供语义标签和足够点击区域。
- 图表必须同时提供文字汇总，不能只靠图形传达金额。

## 19. 测试策略

### 19.1 单元测试

- 十进制金额字符串转整数分

- 多笔退款与退款上限
- 发薪日为 29、30、31 时的月底计算

### 19.3 备份测试

### 19.4 Widget 与集成测试

- 首次启动完整流程

## 20. 性能目标

V1 按个人多年使用规模设计：

- 10 万条流水仍能按周期分页查询。
- 首页不加载全部流水，只执行聚合查询和最近记录查询。
- 流水列表分页或按窗口加载。
- 报告聚合尽量在 SQLite 中完成，避免把全部记录读入 Dart 再求和。
- 冷启动不执行备份扫描或全库重算。
- 导入、导出和大规模迁移避免阻塞主 UI。

## 23. 版本管理与开发约定

- `main` 始终保持可构建。

- 一个提交只解决一个清晰问题。
